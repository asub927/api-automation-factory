Grounding Context

Codebase Context

api-automation-factory compiles MCP tool surfaces plus Spring/OpenAPI contracts into deterministic Playwright + Zod dual-lane suites, delivered as propose-only PRs. Onboarding is already shaped as contracts/<service>/ (manifest + OpenAPI lockfile + MCP tools). Live targets today are a flat Node demo fixture and JSONPlaceholder — not Spring. Experiment research already names Tier E (springdoc / Petclinic + thin MCP adapter) as the closest production shape; the user now wants to own that shape.

Seed repo asub927/spring-service is nearly empty (README / LICENSE / Java .gitignore). The factory has zero .gitmodules and zero Java sources. v1 ingest rejects openApi.mode=fetch; lockfiles must be committed. mcpClient.ts hardcodes only demo and jsonplaceholder.

External Context

Prior art: spring-petclinic / microservices, piomin springdoc multi-service demos, small order/inventory/payment samples, generic_spring_service 3-layer templates. Prefer 2–3 synchronous REST services over full Eureka stacks. Spring AI MCP exists but public samples are tool servers, not REST + OpenAPI dual-lane. Git submodule pain is real; user still requires submodules.

1. Enforced 3-layer archetype from spring-service

Service architecture shape Confidence 88% Complexity Medium

Keep asub927/spring-service as a read-only archetype chassis (not a live business app). From it, generate or fork target repos that always ship @RestController → @Service → repository boundaries, stable operationIds (and optional x-mcp-tool-name), springdoc, and an explicit ban on Spring Data REST auto-exposure. Every future factory target clones this spine instead of inventing package layout.

Basis

direct: seed repo is empty template only; factory has no Java / no @RestController; demo fixture is a flat Node handler. external: generic_spring_service ExampleController/Service/Repository template; Tier E expects real Spring controllers/DTOs.

Rationale

Without an enforced shape, each submodule re-decides layering and OpenAPI operation naming — the factory then compiles against contracts that do not match how production Spring teams organize code.

Downsides

Generator/maintenance cost; archetype upgrades must not silently break pinned targets.

2. Orthogonal gauge-block calibration farm

Service architecture shape Confidence 84% Complexity Medium

Ship 2–3 classic 3-layer Boot apps named by factory stress axis, not ecommerce domain: e.g. rich nested DTOs + validation, Bearer auth + mutating tools (KTD8), and a deliberate springdoc gap (KD7 floor). Prefer in-memory repositories and fixed localhost ports — no Eureka/Config/MySQL. The workspace is a calibration set the factory measures against.

Basis

direct: experiment ladder Tier E; plan “fixture before multi-service”; grounding prefers 2–3 sync REST over Petclinic mesh. reasoned: metrology gauge blocks / pharmacopeia reference standards — specimens exist to validate the assay (the factory), not to be product apps.

Rationale

A single Spring demo only proves “it boots.” A graded farm proves the failure modes the factory claims to handle (Zod richness, mutation fail-closed, MCP coverage floor).

Downsides

Less impressive as a “microservices showcase”; stakeholders may push for domain sagas prematurely.

3. Parent-owned contracts, submodule-only Java sources

Workspace and git submodule topology Confidence 86% Complexity Medium

Create a thin workflow/workspace superproject whose .gitmodules pins the archetype plus each target service. The parent owns all factory-facing artifacts (contracts/<service>/, support YAML, port map). Submodules own only src/ and their export CI. Adding a service = pin submodule + drop manifest — not nested contract hunting.

Basis

direct: zero .gitmodules today; multi-service is already contracts/<service>/ + generated/<service>/; compileService resolves manifests under the factory repo root. reasoned: BioBricks-style chassis + accessioned parts — standard scars, independent pins.

Rationale

Honors the user’s git-submodule requirement while keeping the factory’s existing contract layout as the single handoff surface.

Downsides

Submodule UX (detached HEAD, two-step push) remains; needs clear onboard docs/script.

4. Springdoc export → digested lockfile conveyor

Contract handoff to factory Confidence 90% Complexity Medium

Each Spring submodule CI exports /v3/api-docs to a known artifact path. A workspace sync step copies into contracts/<service>/openapi.yaml, runs derive-mcp-from-openapi.mjs, and records digests per KTD15. Propose/compile never scrapes live OpenAPI — matching v1’s hard lockfile-only ingest.

Basis

direct: src/ingest/openapi.ts throws on mode=fetch; plan KTD2 (exported OpenAPI primary) and KTD15 (digest/URI in PR body); derive-mcp script already exists for operationId bridges.

Rationale

Owning Spring only pays off if OpenAPI arrives the way the factory already compiles. Manual curl-and-commit across N submodules is the recurring operator tax.

Downsides

Two-repo choreography until automation exists; stale lockfiles if sync is skipped (mitigate later with a gate, but don’t block v1 on that).

5. Dual-lane Spring truth source + generic MCP client

Dual-lane MCP surface Confidence 82% Complexity High

Each target Boot app exposes classic REST and an in-process HTTP MCP endpoint (mirror fixtures/demo-service’s same-port /mcp), dispatching to the same @Service methods — optionally factored as a shared starter submodule. In the factory, replace callMcpTool’s demo/jsonplaceholder hardcodes with manifest-driven / xFactoryHttp dispatch so onboarding a third Spring service is not a TypeScript change.

Basis

direct: demo fixture co-locates HTTP + /mcp; mcpClient.ts throws unknown MCP service for anything else; Tier E names thin MCP adapter; grounding notes Spring AI MCP samples are not REST+OpenAPI dual-lane. external: openapi-to-mcp / derive-mcp naming strategy already used for jsonplaceholder.

Rationale

Closes the public prior-art gap and makes owned Spring the dual-lane truth source the product assumes — without a second process per service.

Downsides

Custom /mcp is not full Spring AI MCP protocol; must stay compatible with the factory’s client expectations. Higher implementation burden than derive-only bridge tests.

6. Deliberate drift sibling pair (KD7 teaching target)

Dual-lane MCP surface Confidence 80% Complexity Low

From the same archetype, ship two pins: one with full springdoc enrichment, and one that omits/partials OpenAPI so propose PRs show spring-missing WARN while MCP coverage floor still emits. Treat intentional drift as a first-class specimen, not an accident.

Basis

direct: inventory merge emits spring-missing drift and continues; strategy MCP coverage floor when Spring detail is missing; R6/KD7 dual-lane success criteria.

Rationale

Owning Spring lets you manufacture the failure class the factory claims to handle — before real domain services hide mapping gaps.

Downsides

Easy to misread as a broken service in CI dashboards; needs clear naming and docs.
